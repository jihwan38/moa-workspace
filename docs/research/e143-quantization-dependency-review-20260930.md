## Path A: direct cumulative-sum Main -> VRF (source-legal, not allocation-ready)

Only replace the two cumulative sum terminals: current `Main E4 fetch_cast<F32> -> Mul0(1/factor) -> AddF(old_sum_vrf) -> F32 DM`, then `Sub F32 DM -> VRF`, with the identical vector arithmetic ending `.vector_final().to_vrf(&mut device.sub)`. Natural shape is Time `H/8%120`, Packet `H%8` (eight F32 cells =32B), Element `H%960` (3840B). The to_vrf shape check normalizes `[Time,Packet]` against Element and checks each tensor <=8192B. It does not prove simultaneous allocation or in-place aliasing.

Installed SDK0.8.1 `furiosa-opt-std/src/engine/collect.rs:103–115` exposes Main `to_vrf<Element:M>(self, &mut TuContext<Sub>)`; `engine/mod.rs:305–306` allows Collect and VectorFinal; `furiosa-opt-lower/src/verify/engine/collect.rs:241–278` implements exact normalized-shape/size verification. C11 `c11-ffn-partial-vrf/two-row-v1/mlp.rs:39–54` actually exact-compiled native -> Mul0 -> VectorFinal -> Main.to_vrf using an eight-cell packet. Its schedule shows Main+Sub+VE occupancy, static +3.55%, no NPU run. It proves this general terminal can lower, not that this new residual update can alias old/new VRFs. The installed public source inspected does not expose the named backend VectorConsumer conversion branch; C11's emitted result and the matching32B packet are the available evidence. No hidden “8 bytes” packet limit is inferred from eight cells.

Removed logical traffic would be two 1.875MiB F32 temporary writes and two1.875MiB reads:3.75MiB each direction. Added coupling: the arithmetic producer also reserves Sub, and must read old residual while writing the new residual.

Actual v2 schedule residual VRFs T119/T129/T135 have consecutive lifetimes17783–19487 /19487–21472 /21472–22736, all reserving per-slice[4352,8192). Separate DM production permits this reuse. During the proposed direct replacement old+new require7680B unless true in-place lowering is proven. Already-live tensors on head-owning slices include quant scale T11332B, coefficients T12332B, V channel scales T781024B, Q norm gamma T901024B, and head common scale T12432B. Total prospective occupancy=9824B, exceeding8KiB. These figures use actual schedule reservation addresses/512 and respect sparse head ownership; they are not an assertion that every slice holds all fields. Delaying other producers or supported in-place aliasing could change the result, but neither has been demonstrated. Splitting into480 does not fix this if the old960 and complete new960 allocations still overlap.

**Disposition:** preserve as conditional local dataflow replacement, not the next selected compile. Before an implementation, require a concrete allocation/lifetime solution and a runtime profile showing that this dependency delays completion. C11 is a precedent, not a positive performance result or a proof of alias safety.

## Path B: fuse K4 max -> pow2 scale; investigate scale distribution only if runtime warrants it

The current K4 inter-slice max writes a32B scalar per leader, then a separate Main fetch applies exponent mask and multiplication by1/128. The public InterFirst pipeline permits `vector_inter_slice_reduce(Max) -> vector_intra_slice_tag -> reinterpret/Logic(BitAnd) -> Fp(Mul0)` (`engine/vector/tensor/vector_tensor.rs:649–677` plus stage transitions). Keep the existing local max/floor2^-119, K4 grouping and mask; emit the same leader scale. This removes one small DM scalar handoff and one Main stream, with no new VRF tensor and no changed quantization expression. Actual full lowering is still untested. Static scale generation spans282cycles; it is not a claim of reclaimable whole latency.

The bigger dependency in this area is leader-scale typedDMA sharing the TDMA schedule with weights. A public Sub/Main Switch -> Collect -> VRF route could in principle distribute the same four-way group scalar without that TDMA, but the exact broadcast geometry and whole register schedule have not been demonstrated. C03 has exact source precedent for Sub Switch -> Collect -> VRF (`c08-fused-qkv/c03-columns8/projection.rs:30–36`), distinct from the failed historical Sub Switch -> TRF. It is not evidence that every new CustomBroadcast4 configuration lowers. This path would add Switch/bitmap/context work and must retain the separate head-scale value and unchanged native/common-scale order. Do not add this uncompiled route to an estimate as if distribution were free.

**Disposition:** the pure max/scale fusion is a small source-supported possibility; routing the scale is a conditional feasibility question. With measured Q/K native waiting for weights, neither takes priority over repairing weight ingress. No constant API, term-count sweep, approximate mantissa split, or generic “fuse memory” proposal is selected.

## Weight-ingress topology cross-check for the other reviewer

The initial read-only inference predicted that Slice `[Group64,Row/8=4]`, Time `[K4,Row%8]`, `InterTranspose{4,1,8}` would emit canonical Row. **E144 fullh-v1's actual MIR subsequently disproved that prediction**: `Switch OutTime mismatch: expected (QkvQueryRow % 8, QkvQueryRow / 8), got QkvQueryRow`. Output time is inner row first, former slice owner second: `4*r+b`, not the initially predicted `8*b+r`. C03's `{8,1,1}` precedent did not distinguish these orders and was insufficient to establish the larger-time-factor topology.

The selected concrete correction uses input Slice `[Group64,Row%4]`, Element `[Row/4,H]`, Time `[K4,Row/4]`. The same Switch's expected output `[Row/4,Row%4]` now matches canonical Row. Each source slice owns stride4 rows, with a complete contiguous H3840 row per packet; this is not the original slice's contiguous row block. `config_collect` only checks normalized stream equality and cannot reorder the incorrect v1 row order for free. E144 fullh-v2 exact compile has now passed (static50510; QKV image206592B, SHA256 `687f1c8df3ccf24eee1e9425a64c685148620e09c4a245d4b039231380f3bc53`). That establishes actual full-path lowering for the corrected source, not descriptor, arithmetic, or NPU performance success. Gate and hardware validation remained pending at this correction.
