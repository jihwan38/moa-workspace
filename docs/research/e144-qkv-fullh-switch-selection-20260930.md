# E144 selection: canonical full-H weight ingress and in-stream native routing

Source/SDK audit on E142 (`baseline/e142.json`, source `b3fe0ab4be2a5ece6382ae5745112722200f1b66`). At selection, no E144 compile or NPU run exists. D-E143 names-only measurement136455 completed and its records are integrated into main. This document selects one complete E144 candidate on a new named branch; it is not an adoption decision.

**One preferred structural candidate:** retain E138 v2's weighted four-E4 activation TRF, Term/K4 F32 reduction and canonical scale/head/cache suffix, but replace K4-strided HBM ingress with canonical full-H row-owned E4 DM and an in-stream Main Switch into the native consumer. It is a coupled operand-ownership/ingress repair of E138, not a new precision method or a free prepack. The exact target composition remains uncompiled.

## Actual caller, layout and completion edges

Current `furiosa-opt-gemma4-12B/src/ops.rs:58–86`: BF16 input→sharded pre-RMS→full-H ring32 broadcast→`project_query` and `project_key_value`→query/key/value RMS→RoPE→Q store/K,V scatter. `src/device/sliding/projection.rs:7–154` uses BF16 activation TRF and E4→BF16 lookup on streamed weights. Channel scale applies to complete F32 dot before first BF16. Original rows are interleaved: slice `8a+b`, local Q row `r` corresponds to `2048c+64a+8r+b`; KV is `1024c+32a+8r+b`. The source does not give each slice eight/four canonical adjacent rows.

Frozen `candidates/qkv-native-consumer-local/native-v2/ops.rs:58–75` keeps pre-RMS/head/cache semantics, calling `project_qkv_native`. `native-v2/projection.rs:178–216` routes BF16 ring seeds, quantizes128 identical H3840 row groups, loads one shared E4 TRF `[Term4,H960]` plus four coefficients. Q/K/V share that exact TRF/slice type. `project_native_query:219–264` and `project_native_kv:267–311` have full-matrix weight DMA→one Main native stream→Term4 weighted F32 reduction→K4 sum→compact F32 q0 rows→typed canonical gather→common s→channel scale→first BF16. No BF16 weight materialization or weight TRF exists in E138.

Native ownership: cluster `c`, slice `4g+q`, Q row `2048c+32g+r` (`r<32`), KV row `1024c+16g+r` (`r<16`), weight column `960q+u` (`u<960`). HBM Q15MiB/K7.5MiB/V7.5MiB each read once. Actual native-v2 graph weight operators are Q DmaCommand#O78, K#O91, V#O104 (graph keys104/141/77). Schedule executes V ingress127/native260, Q ingress198/native273, K ingress323/native405 despite source call order Q,K,V. Do not infer issue priority from `let` order.

The current native graph's each Main weight input is produced by its full `Dma.DtoS`; it has no chunk-ready token. Installed public `TuContext::begin` (`std0.8.1/src/context.rs:86–92`) accepts DmTensorView, not HbmTensorView. `HbmTensorView::to_dm` provides a DM result. No supported API to have the native engine consume a partially completed whole weight DMA was found. This describes this graph/API dependency, not an assertion that the hardware TDMA is internally atomic. Explicit staged allocations/transfers could change that dependency but add task/setup/completion edges; source statement reordering is not a demonstrated solution.

## Exact candidate ownership and stream contract

Let `R=8` for Q, `R=4` for KV, and native Row extent `4R`. Use the **existing native row axis factored into quotient/remainder**, not independent owner/local symbols that require an unsafe stream reshape.

1. E4 weight HBM wire view `[Dummy2,Group64,Row(4R),H3840]`→DM `Cluster=Dummy2`, `Slice=[Group64,Row/R]`, `Element=[Row%R,H]`. Source slice `4g+b` owns global row `2048c+32g+8b+r` (Q), or `1024c+16g+4b+r` (KV), and fullH. This is canonical E136 ingress mapped to the new axis spelling.
2. Main fetch `Time=[H/960,Row%R]`, `Packet=[H%960]`. Packet q reads source local DM offset `3840r+960q+u`. Q has32 such960B packets per slice, KV16; total weight read30MiB remains. K-quarter outer/row inner is deliberate: simply fetching row outer would produce a different output row order.
3. `.switch::<m![Group64,H/960],m![Row]>(InterTranspose {slice1:4,slice0:1,time0:R})`: exchange source slice-low `b` with Time K-quarter `q`, preserve group/c/within-row u. Destination `(c,4g+q)` receives Time row `bR+r` and same original weight. Factorization `Row/R,Row%R` is the same named Row axis in canonical order; avoid a generic unsafe TuTensor reshape.
4. `.collect::<m![Row,H/32%30],m![H%32]>()`→exact existing E138 `.contract_outer` with activation TRF Slice `[Group64,H/960]`, packet64/K-time15, laneTerm4. Coefficient multiplication, Term sum, K4 sum, q0 output, pair8B F32 commit, head gather/s/common/channel scale and firstBF16 remain unchanged.

Support evidence: `std0.8.1/src/engine/switch.rs:64–78` explicitly preserves Packet; `engine/mod.rs:301,308` allows Switch→Collect→ContractOuter; `engine/contraction/outer/mod.rs:124–141` requires the exact same Chip/Cluster/Slice mapping as TRF. Existing E55/E137 row scale Switches prove InterTranspose on target in other pipelines; E136 proves canonical plain E4 fullH ingress; E138 proves shared Term4 TRF/native/final reduction. Independent literature review confirms the public InterTranspose formula: source slice4g+b/timeRq+r becomes destslice4g+q/timeRb+r for config(4,1,R). The installed config_switch delegates to binary FFI, so this is a source/topology argument, not an executed shape check. **No actual target compile yet proves this exact Switch→native composition, its config/topology or sequencer/register encoding.** C10 failed BF16 lookup→Main weight-TRF lowering and does not disprove this Main streaming route.

## Removed/added full-path work, prior distinction, first gate

HBM weight bytes remain30MiB, weight DM write/read remain30MiB each, native contraction/quantization/coefficients/head arithmetic counts remain unchanged. The proposed change is placement of row/K permutation: replace strided960B HBM-to-consumer routing with canonical contiguous fullH HBM-to-row-owner routing plus Main Switch on the already required weight read. No additional whole30MiB transpose materialization is intended. It adds Switch setup, routing/collect buffering, a different DM reader order, and possible backpressure/resource overlap; those may lose more than ingress gains. No promised latency saving or rank result.

C03 changed cluster-local head/cache ownership, not this ingress/consumer edge. C09 staged O row60/60 and added native tasks; this proposal keeps one native per Q/K/V. C08's joint allocation/compact-copy repair creates projection assembly and a joint dependency; none is included. E136 loaded30MiB weight into TRF; none is included. E138 v1→v2 changed BF16 activation routing; this proposal fixes four terms and activation preparation and changes original weight ownership only. E130 Main/Sub head separation is not selected. Do not transfer any historical whole speed or numerical proof automatically.
