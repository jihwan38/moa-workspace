[계산·출처·브랜치 근거](top10-audit-evidence-20260927.json),

가능한 구조를 모두 시험했다는 결론은 근거가 부족하다. 실제 실패 패턴은 작은 입력 이동을

FFN 주변 국소 변경을 계속하는 전략으로 현재 10위권 격차를 닫기는 어렵다.**

## 1. 목표를 현재 점수에 맞춰 다시 계산

공식 API를 **9월 27일 00:41:53 KST**에 읽었다.
[응답 원문](top10-leaderboard-20260927.json)은 BEEF **52/69위, 5.926577×**,
10위 **8.859047×**를 반환한다. 과거 3위 목표 대신 현재 사용자의 10위 목표로 계산했다.
[공식 리더보드](https://micro2026-moa.github.io/leaderboard.html).

| 커널 | BEEF 공식 cycles | 당시 10위의 cycles | 그 커널 값까지 필요한 감소 |
|---|---:|---:|---:|
| QKV | 104,091 | 78,870 | 24.23% |
| O projection 경로 | 51,565 | 30,228 | 41.38% |
| FFN | 335,987 | 226,475 | 32.59% |

이는 한 팀의 성능 벡터이지 각 열을 반드시 맞춰야 하는 독립 조건이 아니다.
점수는 세 커널 speedup의 기하평균이므로 필요한 것은 현재 대비 **1.4948배 점수**,
즉 세 커널 cycle 곱의 **3.3400배 감소**다. 균등하게 개선한다면 각 커널33.10% 감소에 해당한다.

- QKV/O를 고정하고 FFN만 바꾸면 **100,594 cycles**가 필요하다. FFN을 두 배 빠르게
  만들어도 점수는 **7.4670×**로 당시10위에 못 미친다.
- 세 커널 각각5% 감소해도 점수는6.2385×다. 단일 커널5% 감소는 점수 약1.72% 개선이다.
- 예시 설계 목표 `(QKV 70k, O 35k, FFN 210k)`는9.0027×다. 실제 측정이나 미래 순위
  보장이 아니라, 필요한 변화의 규모를 보여주는 수치다.

따라서 FFN의 절대 cycle 비중을 점수 가중치로 쓰면 안 된다. 같은 비율의 감소는
QKV/O/FFN에서 점수 기여가 같다. **QKV/O의 큰 병목을 찾는 작업을 FFN과 병행해야 한다.**
최종 평가는 동일 조건 재실행이며 마감 전 마지막 제출을 사용한다. 마감은9월30일23:59 AoE,
한국 시각10월1일20:59다. [9월23일 공식 공지](https://micro2026-moa.github.io/index.html).

## 3. 현재 커널에서 실제로 비용이 발생하는 곳

진입점은 [ops.rs](../../furiosa-opt-gemma4-12B/src/ops.rs)의
`sliding_project_qkv`, `sliding_attention_output`, `decoder_feedforward`다.
FFN의 대표 흐름은 다음과 같다.

```text
HBM residual → BF16 pre-RMS
 → E5M2 3항 입력 준비 → 양 cluster/512 slices 배포 → TRF

up/gate: FP4 HBM → FP4 DM → 전체 E5M2 DM → native dot
         → block16 F32 partial DM → scale×partial/reduce → BF16 up/gate
         → GeGLU → down 입력 재배포

down: FP4 HBM → FP4 DM → 전체 E4M3 DM → BF16 lookup/dot
      → block16 F32 partial DM → scale/reduce
      → BF16 projection → down global scale → BF16
      → post RMS → residual/layer scalar → HBM
```

핵심 구현은 [mlp.rs](../../furiosa-opt-gemma4-12B/src/device/shared/mlp.rs)의
`prepare_ffn_fp8_split`, `broadcast_ffn_quantized`, `project_up_and_gate`,
`project_rows_with_scale_contraction`, `project_down_sharded`다.
현재 up/gate는 native FP8이고 down은 BF16 dot이다. “FFN FP8화”로 묶으면 비용 경로를 놓친다.

H3840/L15360에서 세 projection의 논리 payload는 packed FP4 **84.375MiB**,
block scale **10.547MiB**, 생성되는 FP8 intermediate **168.750MiB**,
F32 block partial **42.188MiB**다. 뒤의 두 수치는 각각 DM에 기록하는 tensor 총량이며
읽기·padding·중복 transaction을 포함한 실측 traffic이나 동시 점유량이 아니다.
QKV/O는 이미 FP8 lookup→BF16 dot을 연결하므로 전체 BF16 weight 저장 제거를 새 제안으로
내면 중복이다. [projection.rs](../../furiosa-opt-gemma4-12B/src/device/sliding/projection.rs).

[기존 whole-FFN NPU trace](../../moa-dev/experiments/candidates/e104-weight-path/README.md)는
다음을 실제 관측했다. 이번 감사에서 새로 측정한 수치는 아니다.

| 구간 | 관측 duration 규모 |
|---|---:|
| Up / gate FP4 적재 | 각각48k cycles |
| Down FP4 적재 | 66k |
| 전체 FP8 변환·DM 저장 | 각각20–21k |
| Up / gate native dot·입력scale·partial 저장 | 각각12k |
| Down BF16 lookup·dot·partial 저장 | 41k |
| 입력3항 ring32 방송 | 23.4k |
| pre-RMS 완료→activation amax 시작 Main 공백 | 42.2k |

이들은 중첩 및 대기를 포함해 합산할 수 없다. 42.2k도 제거 가능한 시간으로 확정할 수 없다.
해당 trace는 원본 control보다 전체가1.3–1.5% 빨랐고, marker 대응은 연산 종류·순서에 근거한다.
bank stall counter나 순수 engine service time은 제공하지 않는다.

이 근거가 지지하는 판단은 **dot 자체의 미세 개선보다 weight 준비·중간 표현·입력 준비의
실제 완료 의존성을 바꿔야 한다**는 것이다. “HBM bank conflict가 몇%”라는 주장은 아직 못 한다.
QKV/O에는 이 FFN과 같은 수준의 현재 image 내부 NPU 비용 귀속 자료가 부족하다.

정렬도 실제 전송 단위로 봐야 한다. QKV FP8 row pitch3840B는256B 배수다.
Up/gate packed 한 row1920B만 보면 정렬이 나빠 보이지만 현재 한 slice의30행 연속
논리 구간은57600B, 즉225×256B다. 이것이 최종 descriptor의 모든 packet을 검증했다는 뜻은 아니다.
Down의960B packed/120B scale 하위 구간은 자세한
descriptor 확인 대상이지만 destination padding만으로 source 접근이 바뀌지 않는다.
E58/E59는 이미 그 단순 padding으로 이득을 못 얻었다.

## 4. 수정해야 할 실험 방향

**제거한 작업이 현재 비교군에 존재하는지, 소비 완료를 실제로 늦추는지부터 확인한다.**
M01은 E64의 큰 weight 재배치를 줄였지만 E104에는 그 복사가 없었다. 실제 weight 적재와
dot 구간은 줄지 않고 새 partial 이동이 생겼다.
[M01 비용 비교](../../moa-dev/experiments/candidates/m01-partial-remap/README.md).

**타일링은 중간 저장·의존성을 없앨 때 의미가 있다.** M04는 전체 FP8 저장 총량을 유지한 채
DMA35→74, dot3→15가 됐다. C11도 partial DM을 줄이면서 native dot2→30이 됐다.
“작은 buffer”, “작은 tile”, “더 많은 overlap”은 완료 시간 개선의 증거가 아니다.
[M04](../../moa-dev/experiments/candidates/m04-tiled-weight-supply/README.md),
[C11](../../moa-dev/experiments/candidates/c11-ffn-partial-vrf/README.md).

**상대 gap보다 절대 ready 시점을 본다.** M07의 pre-RMS→amax 정적 gap은23250→3793으로
줄었지만 pre-RMS 완료는7511→28971로 늦고 최종 입력 방송도56931→59184로 늦었다.
큰 전송을5개로 나눈 사실이 작은 activation의 우선권을 강제하지 않았다.
M05도 amax는 앞당겼지만 입력 방송 완료는 늦었다.
[M07](../../moa-dev/experiments/candidates/m07-weight-ingress-chunks/README.md).

**정적 일정의 작은 차이로 실제 성능을 판정하지 않는다.** M02의 두 유효 구현은 정적
37413→32382인데 NPU78981→89203으로 반대였다. C09/C11의 정적 종료는 예산 선택이며
“NPU에서 실패한 구조”가 아니다. 모든 정적 후보를 되살릴 필요는 없지만,
새로운 비용 제거 기제가 있는 조합을 과거 static-only 결과로 배제하면 안 된다.

**원인 미확정 오류와 측정된 손실을 분리한다.** M06는 packing을 복구해도 timeout이므로
direct packed aliasing만 원인이라고 할 수 없다. FP4 direct는 single projection이 통과했고
pair 합성에서 실패하므로 native FP4 전체가 불가능하다고 할 수도 없다.
반대로 그 사실만으로 compiler bug라고 확정하거나 이미 실패한 padding/warmup을 반복하지 않는다.

| [T-MAN](https://arxiv.org/html/2511.11248v1), [T-MAC](https://arxiv.org/html/2407.00088v2) | activation LUT로 low-bit dot/dequant를 대체 | Qualcomm vector lookup/CPU SIMD 전제다. RNGD fixed decode LUT는 동적 activation LUT가 아니다 |
| [FLUTE](https://arxiv.org/html/2407.10960v2) | 소비 순서에 맞춘 weight/LUT 배치 | paired decode는 현재도 사용 중. offline 재배치·CUDA 공유메모리는 그대로 이식 불가 |

공통된 유효 방향은 **압축 입력을 소비 지점까지 유지하고, 복호화 후 즉시 계산하며,
scale와 작은 partial을 가까이 유지하는 실행 구조**다. 현재 M04의 작은 타일 저장·재독출은
이 구조와 같지 않다. 다만 위 논문 중 어느 것도 현재 SDK에서 그 경로가 정확하게
실행된다는 증거나 상위10위 속도를 제공하지는 않는다.

설치 SDK0.8.1도 직접 대조했다. `cast.rs`의 floating DPE 타입 조합은 BF16/BF16,
E4M3/E4M3, E5M2/E5M2다. [mixed-dtype 감사](mixed-dtype-dpe-audit.md).
`TableLookupCast`는 FP4→E4M3/E5M2와 FP8→BF16만 제공하고 runtime table 인자가 없다.
따라서 **FP8 weight×BF16 activation 직접 dot, FP4→INT8 fixed LUT, T-MAN식 register LUT를
현재 사용 가능한 최적화로 제안하면 안 된다.**
[공식 Fetch Adapter](https://developer.furiosa.ai/furiosa-opt/book/computing-tensors/fetch-adapter.html).
FlashAttention, KV-cache 압축, MTP, host launch, 새 QAT 모델은 이번3개 고정 커널의 직접 해법도 아니다.

## 6. 다음 shortlist와 실행 순서

아래는 **미검증 설계/판별 계획**이다. 새 실험ID를 발급하거나 구현하지 않았고,
세 가지가 모두 독립적인 새 아키텍처라는 뜻도 아니다.

**첫 번째: QKV/O의 현재 전체 image를 계측하고, 가장 큰 비율을 줄일 수 있는 경로를 선택한다.**

기존 FFN marker 계측 도구를 재사용하되 QKV/O image의 marker 대응과 task bytes 동일성을
각각 검증한다. 입력 준비, weight DMA, lookup/dot, partial 이동, RMS/RoPE/cache/store의
시작·완료·의존성을 본다. 이미 부족한 정보가 무엇인지 명확하므로 새 exhaustive profiler는 필요 없다.
이것은 또 하나의 FFN 진단 시리즈가 아니라 점수의 나머지2/3을 위한 한 번의 판별이다.

tail이 큰 경우의 설계 후보는 `BF16 pre-RMS → 기존 exact dot → head를 소유한 producer에서
F32 scale/첫 BF16 경계 → head RMS/RoPE → cache/output`다. 단순 cluster-local head 소유는
C03가 이미 시험해+1.56%였다. 새 후보는 **typed head gather나 후속 DM 경계를 실제 제거**해야 한다.
BF16 scale/rounding, Q/K/V의 서로 다른 norm, offset/cache 쓰기 계약을 유지한다.
head 소유권 변경으로 생기는 inter-slice norm reduction과 cos/sin 복제도 추가 비용에 넣는다.
dot/weight 공급이 대부분이면 이 tail 설계는 먼저 제외한다. C08 공동 buffer 전체 완료를
기다리는 fusion이나 단순8열 분할도 그대로 반복하지 않는다.

O는 M01/M02의 split-K/partial 이동을 다시 시작하지 않는다. 공급이 병목이면 HBM row
연속성·DMN 순서·dot의 column 소유권을 함께 바꾸되, weight 전체 repack과 새 partial
집결 비용까지 포함한다. 현재 정보로 특정 새 mapping이 빠르다고 선정할 근거는 없다.

**두 번째: FFN direct decode를 살릴 제한적인 hybrid boundary 후보.**

[D-FP4-NATIVE v7c](../../moa-dev/experiments/candidates/fp4-native-boundary/README.md)에서는
공동 producer의 projection0 중 local row0/slices0..7/두 cluster,16행에 오류가 남고
projection1은 검사한 입력에서 통과했다. 기존 padding/warmup과 다른 선택지는,
**projection0의 모든512 slices에서 첫 행을 검증된 materialized 경로로 따로 계산하고,
fused 경로의 나머지 행과 결합하는 고정 shape 분할**이다. 입력값/fixture를 보고 분기하지 않는다.
첫 probe에서는 v7c joint stream의 전체 shape와 계산을 유지하고 projection0 row0 출력만
재계산 결과로 교체한다. fused stream을29행으로 줄이면 기존 오류 좌표·layout의 근거가 바뀐다.
검증된 것은 기존 전체 shape의 materialized 산술이다. 새1행/slice 경로는 미검증이며,
F32 한 원소4B와 DM commit8B 정렬에 필요한 padding 및 최종 merge를 따로 검증해야 한다.

```text
동일 packed FP4 / BF16 입력 준비
 ├─ joint direct decode → native dot → block scale/reduce → 전체 행(row0는 교체)
 └─ projection0 첫 행/모든slice: FP8 DM → 검증된 dot/scale → boundary 행
 → 완전한 up/gate tensor → 기존 GeGLU/down 또는 검증된 M03 local 경로
```

첫 행의 FP8 논리량은1.875MiB로 한 projection 전체56.25MiB의1/30이다.
그러나 추가 HBM 읽기, lookup 설정, dot, partial, scatter/merge 비용은 전부 생긴다.
이 비율을 kernel 절감률로 환산하지 않는다. 첫 feasibility는 동일 입력의 두 projection
**전체 F32 출력**과 독립 oracle을 검사하고, 그 뒤에만 완성 FFN을 평가한다.
일부 오류를 가린다는 이유로 나머지 행의 검사를 생략하지 않는다.

이 재계산 경로는 보존된 실험에서 찾지 못했다. 하지만 allocator/TRF lifetime 오류라면
작업을 추가하는 순간 오류 좌표가 바뀔 수 있다. 그런 경우 무작정 fallback 영역을 늘리지 않고
이 가설을 닫는다. 저수준 원인 규명을 대신하는 입증된 수정도 아니며, 성공하더라도 새로운
전체 조합에 대한 확대 정확도가 필요하다. 큰 중간 저장을 제거하는 경로를 시도할
**조건부 후보**이지 다음 승자를 보장하는 제안은 아니다.

**세 번째: M06는 새로운 지연 추측 대신 실행 실패 기제를 한정해 진단한다.**

공식 메모리 문서는 Main Fetch/Commit, Sub Fetch/Commit보다 DMA 우선순위가 낮고,
같은 bank의 연속 점유가 NoC timeout으로 이어질 수 있다고 설명한다.
M06 v4/v5의 frozen graph에서 공통 sharded RMS→global max→scale broadcast→quantizer와
동시 DMA의 bank 접근·반복·live buffer를 확인하고 firmware 오류/실패 marker와 대조한다.
이는 **M06 원인이라는 확정이 아니라 검증 가능한 가설**이다.

구체적 충돌이 확인되면 quantizer와 broadcast의 producer/consumer 경계를 바꾸는
하나의 수정을 시행한다. 단순 row/packet padding sweep, SDK 전체 버그라는 결론,
timeout 후보의 정적 수치로 속도를 주장하는 일은 하지 않는다. 증거가 없으면 보류를 유지한다.
이 후보는 입력 준비 경로의 복구이며, 그 자체만으로33% 격차를 닫을 구조는 아니다.

주력은 **QKV/O의 큰 비율 개선 경로 확보 + FFN의 전체 중간 저장 제거 가능성 검증**이다.
M03는 별도의 짧은 채택 검증 대상으로 두고 M05/M07 변형 sweep은 중단한다.
후보마다 source recipe와 성능 control을 따로 기록하고, 제거·추가 bytes뿐 아니라
새 명령 수·whole-stage 대기·partial 경계·정확도 계약을 함께 적는다.
기본PASS와 같은 allocation 앞뒤 비교로 먼저 선별하고, 큰 이득이 있는 완성 경로에
독립 반복/확대 정확도 예산을 쓴다. 이 감사에서는 E104 runtime을 그대로 유지했다.
