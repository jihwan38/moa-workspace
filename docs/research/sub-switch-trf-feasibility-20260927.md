# Sub Switch -> TRF: read-only feasibility result

Conclusion: the public SDK can express the chain, but there is no verified successful lowering in the inspected call sites. The closest exact candidate already failed. Therefore this is an unresolved routing/lowering question for future work, not a ready replacement for replicated-activation DM. No compile, prototype or NPU was run for this review.

- `qkv-bf16-broadcast-trf-e55/projection.rs:17–22` already implements `Sub.begin(leaderDM) -> fetch(Time1,PacketH3840) -> CustomBroadcast32(OutSlice=Dummy256) -> collect -> TRF`. Its frozen `artifacts/qkv-bf16-broadcast-trf-e55/compile-attempt1.log:34` rejects `Switch snoop bitmap disagrees with the (OutSlice x OutTime) enumeration at output slice 1`. No image/graph/schedule exists for that attempt. This is the relevant direct-broadcast precedent; it is separate from C10.
- `c10-direct-weight-trf/direct-v1/projection.rs:23` attempted Main FP8 lookup -> BF16 collect -> weight TRF. Its frozen `evidence/c10-direct-v1/compile.log:35–36` reports `lower_fetch_unit` / `renegade feature is enabled in non renegade-s config`. Plain Sub E4 input avoids that particular Main lookup edge, but does not resolve the E55 bitmap failure.
- `m06-sharded-input-pipeline/sharded-packed-v4/mlp.rs:440–455` gathers terms to leaders, uses Main CustomBroadcast32, commits full replicated DM, then reshapes. Lines107–110 later use a separate ordinary Sub load to TRF. v4/v5 whole FFN timeout therefore neither proves nor disproves direct Sub Switch -> TRF support. E134's retained FFN broadcast path has the same materialization separation.

Installed 0.8.1 API evidence:

1. `furiosa-opt-std/src/engine/switch.rs:57–72` makes `switch` const-context generic and keeps the packet unchanged. `collect.rs:62–86` exposes `Switch -> collect -> to_trf`, also with generic context. These are frontend contracts only.
2. `SwitchConfig::Broadcast01`, `Broadcast1`, `TransposedBroadcast1` and `CustomBroadcast` exist in `furiosa-opt-lower-types/src/switch.rs`, but no inspected exact successful direct-TRF call site establishes an alternative fixed topology for the needed consumer mapping. Replacing one enum with another is not yet an evidence-backed repair.
3. `furiosa-opt-lower/src/lowering/mod.rs:168` forwards `config_switch` through `sys::config_switch`; the installed public wrapper does not expose the bitmap algorithm that would prove a particular new named-axis repair.
4. `furiosa-opt-std/src/tensor/memory.rs:1395–1438` exposes TRF construction/zero/views but no public `TrfTensor::reshape`. `engine/contraction/outer/mod.rs:124–127` requires the streamed operand and typed TRF to have the same Chip/Cluster/Slice types. The proven anonymous-output broadcast layout `[Dummy256/32,32]` cannot simply be used for distinct named weight-row owners by asserting their values are replicas. DM currently supplies the safe materialize-then-physical-relabel boundary.

Bounded source search found only the failed E55 direct chain among candidate Rust source files (excluding duplicate evidence snapshots), and no matching direct chain in installed `furiosa-opt-*0.8.1` Rust sources. This scoped absence is not a hardware impossibility proof.

Native QKV Term4 lanes would additionally require TRF time/element order `[Term4,H3840]` -> Lane4/ElementH3840, payload15,360B per consumer slice. That fits the logical capacity calculation, but does not validate broadcast snoop routing, allocation, lane indexers or NPU arithmetic. A future supported path needs a concrete named-output topology or an actual public register relabel route, followed by exact graph/descriptor and boundary verification. It must still include compact term preparation and leader gathering; deleting the replicated DM boundary does not delete those costs. No latency saving follows from this review.
