# 30위권을 위한 전체 실행 경로 재검토

조사 시작 main `90fa732`, 채택 source E134 `4f8fe7f`, 성능 control `baseline/e134.json`.
[공식 조회](top30-leaderboard-20260927.json)의 BEEF는51위6.1405524×,
30위는7.7711479×다. 다른 팀 점수를 고정하면 세 커널 시간을 각각20.9827% 줄이는 수준이 필요하다.
한 커널만 줄이면50.6637%가 필요하며 FFN만의 목표는155221cycles다. 개선 보장이 아닌 점수 산술이다.

## 선택 기준

실험 단위는 공개 입력부터 최종 출력까지의 완성된 데이터 흐름이다. 논리적 저장 제거량,
중첩된 profile 구간, 과거 서로 다른 control 대비 이득을 더해 예상 speedup을 만들지 않는다.
5% 미만 positive도 제한된 채택 검증 대상이며 추가 파라미터 튜닝과 구별한다.
타일 크기·source 선언 순서만 바꾸는 후보는 이번 주요 연구 대상에서 제외한다.

## 1. E135: 독립 FP4 producer와 현재 fused native 소비자

Source recipe는 E134, 비교군도 별도로 E134를 지정한다. 별도 branch의 실제 시작 commit은
이 조사 기록을 main에 통합한 뒤 recipe에 기록한다. 실행 범위는 full FFN이다.

현재 up/gate 각각:

```text
FP4 HBM → compact FP4 DM → 전체 E5 weight DM
→ 5×6행 native dot / input scale / block scale / F32 H 합산
→ F32 row output → cluster-local BF16·GeGLU → E134 weighted native down → 기존 후단
```

선택할 경로:

```text
up/gate 각 원본 FP4 HBM → 각각 compact FP4 DM
→ 각6행 view의 FP4 lookup → native dot → input scale → block scale → F32 H 합산
→ 기존 row output·GeGLU·E134 weighted down·후단
```

제거 대상은 up+gate FP8 weight DM 쓰기·읽기 각112.5MiB다. E131의 joint packed 복사와
scale assembly를 추가하지 않는다. Native 시작은 현재와 같은10회지만, FP4 lookup도
10개 stream에 들어가므로 반복 준비·Main/Sub·TRF/VRF 수명 비용을 실제 graph에서 검사한다.
FP4 HBM56.25MiB와 block scale HBM7.03125MiB는 그대로다. 이 바이트는 논리량이다.

이는 direct FP4 가족의 재개이며 새 독립 원리로 세지 않는다. E103은 큰 native dot의 F32
block partial과 별도 복원·scale·합산을 사용했고, 이번에는 현재 fused 소비자에서 즉시 줄인다.
E103의 compact ingress source/schedule은 정상 크기지만 원본 descriptor dump가 없어
그 수치 실패의 정확한 원인은 미해결이다. 단순 TRF reload만으로 고친다고 주장하지 않는다.
v7c의 joint padded-view 초과읽기와 E103 독립 producer 실패도 서로 다른 사건이다.

첫 gate: exact full compile, 실제 descriptor의 FP4/scale bounds와6행 view pitch,
TRF/VRF 주소·수명·lookup 준비 의존성 검사. 통과하면 동시 E134 앞뒤 control로 whole NPU screen.
오류가 나면 처음 잘못된 projection 경계와 mapping을 확인하고 원인이 있는 수리만 진행한다.
Whole positive는 원본 동결 후 추가 입력·projection oracle·독립 반복으로 채택 검증한다.
성능 회귀만으로 전체 direct 가족을 폐쇄하지 않고 추가 비용과 수리 가능성을 기록한다.

## 2. QKV/O: weight 변환을 없애는 native E4 경로의 정밀도 수리

현재 FP8 weight → BF16 lookup → BF16 activation dot은 lookup/table 준비를 유지한다.
SDK0.8.1은 E4×E4와 E5×E5를 지원하지만 E4×BF16이나 E4×E5는 지원하지 않는다.
따라서 mixed dtype을 가정하는 해법은 후보에서 제외한다.

과거 E47의 native E4 두 항은 표준 입력에서 빨랐지만, column-local outlier/작은 값
상쇄 반례에서 실패했다. Amax를 column별로 나누는 방법도 이미 그 구현에 있었다.
현재 검토 대상은 더 넓은 범위를 다루는 weighted spatial terms와 F32 복원을 조합하고,
현재의 channel scale 후 첫 BF16 변환 경계를 유지하는 완성 O 경로다.
4개 lane 사용이 공짜라는 가정은 하지 않는다. 실제 추가 양자화·TRF·lane fold·term sum과
K-column 합산 비용을 포함해야 하며, 과거 반례에 대한 CPU/실제 NPU 검증이 필요하다.
정확한 decomposition과 emitted layout이 확정되기 전에는 새 성능 후보로 단정하지 않는다.

## 문서와 설치 SDK의 역할

- [Furiosa Outer](https://developer.furiosa.ai/furiosa-opt/book/computing-tensors/contraction-engine/outer.html):
  supported operand pairs와 stream broadcast/reuse. 문서의 지원은 정확한 조합의 lowering 성공과 다르다.
- [Fetch Adapter](https://developer.furiosa.ai/furiosa-opt/book/computing-tensors/fetch-adapter.html):
  dtype 기반 lookup과 Main/Sub 제약. FP4 static table 설명을 FP8 table 준비 비용이 무료라는 주장으로 확대하지 않는다.
- [Schedule](https://developer.furiosa.ai/furiosa-opt/book/scheduling/schedule.html):
  실행 graph와 공유 자원. source 선언 순서만으로 실행 우선권을 보장하지 않는다.

이 문서는 후보 선택 시점의 기록이다. 이후 compile/NPU 결과는 각 후보의 recipe·decision·원본 로그에
남기고, 최종 채택과 큰 구조 연구의 결론을 별도로 갱신한다.
