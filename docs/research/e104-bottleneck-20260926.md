# E104의 현재 격차와 FFN 병목 후보

후속: [E104 내부 NPU 진단](../../moa-dev/experiments/candidates/e104-weight-path/README.md)을
실행했다. 아래는 실행 전 조사 기록이며, 최신 실측과 설계 결론은 후속 문서를 따른다.

조사일: 2026-09-26. `opt/m02-cluster-k`의 `a46baa4` 이후 보완 조사다.
실행 소스는 E104이며 이번 작업은 기존 소스·정적 schedule·NPU 기록 대조와 웹 조사다.
새 compile, Arena 진단, 후보 채택 또는 공식 제출은 하지 않았다.

**현재 개선 우선 대상은 FFN이다. 내부에서는 weight 공급·준비 경로가 가장 강한
병목 가설이지만, HBM 적재·FP4 변환·DM 왕복·activation 준비 중 어느 비용이 실제
NPU 완료 시간을 가장 많이 늘리는지는 아직 분리 측정하지 않았다.**
기존 비용 진단도 정적 분석에서 멈췄다. M01/M02는 O projection 실험이므로 그 결과로
FFN의 데이터플로나 메모리 매핑에 문제가 없다고 결론낼 수 없다.

## 1. 현재 공식 제출끼리 비교한 격차

[공식 리더보드](https://micro2026-moa.github.io/leaderboard.html)의 HTML에 명시된
API를 Docker 네트워크에서 읽었다. [응답 원문](../experiments/leaderboard-20260926-092533Z.json),
[출처·해시·계산](e104-bottleneck-20260926.json).
캡처 파일 시각은 2026-09-26 09:25:33 UTC / 18:25:33 KST다.
69팀 중 BEEF는52위, `6ee0120a` / SDK0.8.1 / 5.926577×다.
3위 EoM은 `57afb94a` / SDK0.8.1 / 9.251393×다.

| 커널 | BEEF cycles | 현재 3위 cycles | 해당 3위 값에 도달할 감소율 |
|---|---:|---:|---:|
| QKV | 104091 | 66611 | 36.01% |
| O projection 경로 | 51565 | 36234 | 29.73% |
| FFN | 335987 | 196435 | 41.53% |

공식 식은 세 baseline speedup의 기하평균이다. 3위 점수는 BEEF의1.561배이며,
9.25배는 원본 baseline 대비 값이다. FFN은 이 세 커널 cycle 합의68.34%지만
점수 가중치가68.34%라는 뜻은 아니다. 같은 비율의 개선은 세 커널에 같은 점수 효과가 있다.
FFN만 현재 3위 수준으로 줄여도 나머지가 같다면 점수는 약7.088×다.
최종 순위는 공통 조건에서 재평가되므로 이 표는 현재 공개 제출의 격차다.

## 2. 실제 실행 경로와 남아 있는 작업

[`ops::decoder_feedforward`](../../furiosa-opt-gemma4-12B/src/ops.rs#L212)는
pre-RMS → `feedforward_sharded` → post-RMS → residual/layer scale → HBM 저장을 호출한다.
FFN 내부는 다음 경로다.

```text
BF16 activation → 세 E5M2 항 생성 → ring32 방송 → projection별 TRF 적재
FP4 up/gate HBM → FP4 DM → E5M2 전체 weight DM → native dot
    → F32 block partial DM → block scale 곱·합산 → up/gate gather → GeGLU
FP4 down HBM → FP4 DM → E4M3 전체 weight DM → BF16 lookup·dot
    → F32 block partial DM → block scale 곱·합산 → 출력
```

근거는 [`project_up_and_gate`](../../furiosa-opt-gemma4-12B/src/device/shared/mlp.rs#L75)의
92–95, 116–119행 FP8 `.commit()`과,
[`project_down_sharded`](../../furiosa-opt-gemma4-12B/src/device/shared/mlp.rs#L358)의
396–403행 FP8 `.commit()`이다. 각각 이후 dot stream이 저장된 FP8 tensor를 다시 읽는다.
[`project_rows_with_scale_contraction`](../../furiosa-opt-gemma4-12B/src/device/shared/mlp.rs#L30)은
16원소 block dot을 F32 DM에 저장한 뒤 별도 stream에서 scale 곱과 합산을 수행한다.
세 activation 항을 사용하지만 이것만으로 weight DM을 세 번 읽는다고 해석하지 않는다.

`H=3840`, `L=15360`과 현재 dtype에서 계산한 **논리 데이터량**:

| 항목 | up/gate/down 합계 | 의미 |
|---|---:|---|
| packed FP4 weight | 84.375 MiB | 세 weight의 HBM 입력 payload |
| E4M3 block scale | 10.547 MiB | 16 weight당1개 scale |
| 전체 FP8 weight 중간 결과 | 168.750 MiB | 세 연산을 통틀어 DM에 기록하고 소비하는 payload |
| F32 block partial | 42.188 MiB | 세 projection의 scale/reduction 전 중간 결과 |

세 행렬이 동시에 전부 살아 있다는 뜻이 아니며 padding·중복 전송·실측 bus traffic은
포함하지 않는다. 데이터량을 그대로 지연이나 절감률로 바꾸지 않는다.

## 3. weight 준비를 먼저 의심하는 정적 근거

[재현 가능한 E104 정적 분석](../../moa-dev/experiments/diagnostics/e104-cost-attribution/README.md)의
원본 schedule/source hash를 다시 검사했다. 같은 up projection의 순서는 다음과 같다.

| 작업 | 정적 시작→종료 | 정적 duration |
|---|---:|---:|
| FP4 HBM→DM | 47853→72465 | 24612 |
| FP4→E5M2 변환·전체 DM 저장 | 72471→81734 | 9263 |
| native dot·입력 scale·F32 partial 저장 | 81737→87421 | 5684 |

이 구체적 경로에서는 weight를 모두 펼친 stream 종료 뒤 dot stream이 시작한다.
행렬 적재와 변환이 dot보다 긴 것은 **weight 준비 경로를 우선 조사할 근거**다.
입력 세 항 방송도11783 정적 cycles이며 같은 MainContext를 사용한다.
Down은 weight DMA29427, FP8 변환9263, BF16 lookup·dot·partial 저장18263이다.

전체 정적 makespan157045, Main/DMA 중첩70771이다. 위 시간을 합쳐 제거 가능 시간으로
계산하거나 hardware cycles의 기여율로 해석하지 않는다. 특히 FP8 변환만 제거하면
41.53%가 줄어든다는 근거는 없다. [공식 diagnosis 지침](https://developer.furiosa.ai/furiosa-opt/book/scheduling/diagnosis.html)도
데이터 의존성과 공유 자원 대기를 구분하며 정적 schedule이 장치 처리량의 증거는 아니라고 설명한다.

## 4. 바로 연결되는 공개 자료

- [GPU MODE / NVIDIA NVFP4 GEMV 공식 문제](https://raw.githubusercontent.com/gpu-mode/reference-kernels/main/problems/nvidia/nvfp4_gemv/task.yml):
  B200의 FP4 행렬·벡터와16원소 E4M3 scale, 공개 shape·평가 코드가 있다.
  저비트 GEMV의 공급 비용을 보는 데 가깝지만 MOA의 BF16 activation 및 RNGD 실행 모델과 다르다.
- [참가자 본인의 Twelve Attempts at an FP4 Kernel](https://amandeepsp.github.io/blog/nvfp4-blackwell-gemv/):
  저자는 split-K partial/atomic, 넓은 load, accumulator 추가 등의 회귀를 보고하고,
  프로파일 확인을 늦춘 점을 원인으로 꼽는다. 이 사례는 특정 기법이 모든 장치에서
  무효라는 증거가 아니다. 본문에서 재인용한 타 참가자의 방법은 이번 진단의 근거로 삼지 않았다.
- [Marlin 저자 구현·설계](https://github.com/IST-DASLab/marlin):
  weight 적재, dequantization, 소비 명령의 순서와 activation 재사용을 함께 설계한다.
  가져올 것은 이 결합 설계 관점이다. CUDA cache/PTX 설정을 RNGD에 그대로 적용할 수 없고,
  외부에서 미리 weight를 재배치하는 비용을 MOA에서 무료로 제외할 수도 없다.
- [Furiosa Memory Performance](https://developer.furiosa.ai/furiosa-opt/book/moving-tensors/memory-performance.html):
  정렬뿐 아니라 접근 순서, HBM bank/channel 배치, DM interleaving과 공유 자원이 중요하다.
  문서의 일반적인 conflict 사례가 우리 E104에서 그만큼 발생했다는 뜻은 아니다.

국내·다른 해외 대회는 기존 [대회 자료 조사](competition-techniques.md)에 정리되어 있다.
이번에 확인한 범위에서는 직접 재현 가능한 국내 RNGD 커널 대회 수상 구현을 추가로 찾지 못했다.
다른 팀의 실제 MOA 내부 설계는 이 공개 점수만으로 알 수 없다.

## 5. 중복 실험을 피하는 다음 진단

단순히 “FP4 변환을 dot에 융합”하는 것은 새 후보가 아니다.
[C07](../../moa-dev/experiments/candidates/c07-native-scale-dpe/decision.json)에서 직접 연결한 후보들은
별도 projection 검사 일부에서 실패했고, FP8 materialization을 둔 E102/E104는 통과했다.
실패의 내부 원인을 compiler/LUT 버그로 확정하지 않았고, 그 원인을 바꾸지 않은 재시도는 하지 않는다.

다음 판별 질문은 **weight의 HBM→DM 공급, FP8 중간 저장, activation 분배 중 어느 경로를
바꾸면 소비자의 시작/전체 완료를 실제로 앞당길 수 있는가**다. M03 실행 전 해당 설계 선택에
필요한 범위로 제한해 아래 진단을 구현한다. 아직 실행 결과가 아니다.

1. E104의 실제 크기·HBM/DM 배치·dtype·입력을 고정한 weight 적재 경로와
   적재+FP8 변환 경로를 비교한다. 결과 tensor를 검증 가능한 출력으로 소비시키고,
   각 출력 경계·저장 비용과 compiler의 작업 제거 여부를 확인한다.
2. 대응하는 dot과 activation 준비를 연결한 probe로 입력 대기·공유 자원 경쟁을 점검한다.
   인위적인 사전 변환은 진단용으로만 표시하고 최적화 성능으로 세지 않는다.
3. 공급 비용이 지배적이면 HBM access와 weight 소유권을 함께 바꾸는 경로를,
   중간 표현 비용이 크면 타일 단위 변환·소비와 정확도 실패 원인을 함께 다루는 경로를,
   activation 준비가 소비를 늦추면 입력 표현·복제·TRF 소유권을 함께 바꾸는 경로를 우선한다.
   차이가 분명하지 않으면 불확실성을 남기고 큰 parameter sweep으로 확대하지 않는다.

격리 probe 시간의 차이는 full FFN의 절감률이 아니다. 변경된 overlap·출력 경계 때문에
고립된 시간을 더하거나 빼서 병목 기여율을 만들지 않는다. 선택한 전체 구조는 모든 입력
준비·변환을 포함하고, 기존 정확도 기준과 동시기 NPU control로 다시 판단한다.
