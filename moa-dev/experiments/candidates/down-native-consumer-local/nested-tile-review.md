# E140 local-v2/v3 tiled-fetch lowering and flat-index repair

The reported failure is `Fetch: a live input axis is left unread (Time1, Packet TileL%1920=480#1920)` at the first quantizer `commit_view`. The source explicitly fetched30×16BF16 values and collected60×8F32 values; the diagnostic's Time1/Packet480#1920 therefore cannot be identified with that source-level fetch configuration without additional backend IR. No successful image or arithmetic output exists.

Read installed SDK0.8.1 `engine/commit.rs:33–40`: `commit_view` validates slice/commit mapping and calls `dst.inner.transpose(self.inner.view(), false)`. It does not explicitly create a new fetch in public Rust. `tensor/memory.rs:1321–1337` mutable tile calls `config_tile` then `retile`; `tensor/view.rs:134–143` also treats cells outside a mutable tile as Bottom padding. Thus the public source does not prove that an implicit RMW fetch is the exact failing cause. Nested inner-axis tile lowering remains a bounded hypothesis, not a confirmed SDK bug.

A concrete representation repair removes the failing structure while keeping all physical math: after local1920/K4amax, consume the full BF16 allocation through same-wire-order reshape to `[DownChunk4,TileL%480]`. Allocate packed E5 as `[DownPackedChunk12,TileL%480]`. Access one outer input chunk at i; write/read one outer packed chunk at `4*term+i`, each exact480B. No nested mutable tile or fixed480-of1920 inner-axis mapping remains. E138 actual compiled direct-term commit uses this same single-outer-axis window pattern. Finally consume the whole packed allocation through reshape to `[FfnTerm3,TileL%1920]`.

The wire proof is `(4*t+i)*480+u = t*1920+i*480+u` for t<3,i<4,u<480. Cluster Dummy2 and Slice DownColumns are unchanged. These are whole-allocation Element regroupings, not partialview reshapes, permutation or padding-DMA. The final native footprint5760B and all coefficients/reduction remain unchanged. This is a justified source-contract repair worth exact compilation; it is not proof that target lowering will succeed. Emitted literal IndexAccess/IndexWrite offsets and full VRF lifetime must still pass.
