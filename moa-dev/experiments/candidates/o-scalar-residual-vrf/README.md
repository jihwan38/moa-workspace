# E148: O scalar and cumulative F32 supply directly to VRF

Not adopted. Frozen `direct-v1` uses source E147 `fb45202`, actual start `f945162`, independent performance control `baseline/e147.json`. Branch `opt/o-scalar-residual-vrf`. It combines one-Main scale, Sub ring16 scalar/coefficient broadcasts and two unchanged cumulative F32 sums directly into VRF. Native4-term arithmetic, two60-row stages and the whole suffix stay unchanged. Logical sum DM write/read each1MiB disappear; shared16KiB bitmap load and Main/Sub/VE coupling are added.

Whole O regressed in both independent allocations:141077 was43945 versus bracket42546(+3.288206%);141134 was44266 versus42370.5(+4.473631%). The first screen passes45 comparisons; the second bounded profile passes63 including contemporary whole controls and actual current FFN. Standard candidate distinct inputs remain3. Extra6, raw9/34560 exact BF16 and fullcase7/3840 tolerance packages were built but never run on NPU. No official submission or runtime change.

The [actual profile](readiness/profile-analysis.json) observes quantization completion23268.5→10723 and TRF23860.5→12004cycles (each landmark's own median). First native advances, but weight1 completion30182.5→31158 and last native30184.5→31160move later. Both last natives start at weight-end+2 in all6 run/cluster observations. These are instrumented readiness boundaries, not exclusive bus-time attribution or additive savings. The control's45 and candidate's40 operation names are the only image bytes modified by profiling; independent binding checks pass.

Adoption rejects this frozen prototype; further local sweeps stop. The next selected question changes O weight supply using E147's original quantizer: a60-row stage factors into15×4 row owners, each reading contiguous K1024 then Main InterTranspose4 restores the same K256/row60 consumer. This preserves60+60/native arithmetic but adds in-stream routing. It must pass actual descriptor/mapping and whole performance gates. It does not inherit a gain from E144 QKV.

The same profile shows current E142 FFN gate native at shared-TRF-end+1 and down at its TRF-end+1; up/gate already share one emitted TRF despite two source declarations. The small up result gather overlaps a long down-weight load, so removing duplicate source loads is not a valid traffic saving.
